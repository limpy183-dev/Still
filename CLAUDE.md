# Still: notes for agents

Still is a Windows 10/11 x64 focus app. It blocks apps (through AppLocker) and websites (through a Chrome/Edge companion), and it also has to-dos, alerts and session history. Repo: `limpy183-dev/Still`. Website: https://stillfocus.fyi/home

## The suite

| Part | Where | Notes |
| --- | --- | --- |
| Desktop app | `crates/still-app/`, `app/` | Rust (since 2.0.0; the Electron app it replaced was 1.2.0 and older, see `docs/rust-port.md`). `Still.exe` uses wry/tao to show the screens in the system WebView2. The screens are plain HTML/CSS/JS in `app/` (`renderer.js`, `alerts.js`, `websites-ui.js`, `todos.js`, `new-things.js`), embedded into the exe by `build.rs` and served at `https://still.localhost/`. `ui.rs` injects the `window.still` / `window.alarm` bridge the screens call; `app.rs` (preferences, guard client), `alerts.rs`, `websites.rs`, `discover.rs`/`apps.rs` (app scan) do the work. Validation is in `crates/still-core` (`domain`, `alerts`, `websites`, `session`), shared with the guard. |
| Browser companion | `app/browser-extension/` | MV3 extension. It works on its own (settings page `still.html`: its own website list, soft sessions, limits, bedtime, block screen, kept in `storage.own`) and talks to the app over native messaging when Still is set up. Both sides only add blocks and the stricter limit wins, so neither releases what the other holds. The app embeds it, copies it to disk on start and stamps `version_name` with the app version, and the companion reloads itself when that changes (see `crates/still-app/src/websites.rs`). Its own `manifest.json` `version` is separate from the app version. |
| Still Guard (native) | `crates/still-guard/`, `native/` | Rust SYSTEM service `Still.Guard.exe` (`guard.rs` protocol and state, `enforce.rs`, `service.rs`, `cli.rs` install/uninstall, `host.rs` the browser companion's native-messaging host). Session rules and Windows checks are in `still-core` (`session`, `compat`). `native/policy.ps1` writes the AppLocker rules (run by the guard through Windows PowerShell); `native/discover.ps1` is only a fallback for the native app scan. Pipe `Still.Focus.Guard.v1`, service `StillFocusGuard`, `%ProgramData%\Still\state.json`. |
| Installer | `crates/still-setup/`, `installer/` | Rust Setup (`install.rs`, screen in `crates/still-setup/ui/index.html`) that installs, updates and uninstalls per user. `scripts/build.ps1` appends the app to it (`STILLPAY` trailer) to make `Still-Setup-X.Y.Z.exe`; without the payload it is the uninstaller. `installer/` holds its fonts, icon and manifest. |
| Android app (preview) | `android/` | Plain Java, Android framework only (no AndroidX/libraries). An accessibility service blocks apps and (via browser address bars) websites, enforces daily website limits and bedtime, shows block screens, and has the to-do list, session history and alerts (reminders, alarm screens, alert-started sessions with snooze); `Session.java` mirrors `crates/still-core/src/session.rs`, `Websites.java` mirrors `app/websites.js`, `Alerts.java` mirrors `crates/still-core/src/alerts.rs`; the rules are JVM unit-tested. The UI copies the desktop look (Manrope, the olive palette, `app/styles.css` animations) with a bottom bar between the five pages (`Nav.java`). Build/test: `cd android && ./gradlew testDebugUnitTest assembleDebug`. See `docs/android.md`. A signed preview APK (`Still-Android-preview-X.Y.Z.apk`) is attached to each GitHub release by `release.yml` (key in the `ANDROID_KEYSTORE`/`ANDROID_KEYSTORE_PASSWORD` secrets); the Download page (`#android`) links it, and `site.js` points that link at the latest release's APK. |
| Website | `website/` | Static HTML/CSS/JS with no build step. `.github/workflows/pages.yml` deploys it to GitHub Pages on every push to `main` that touches `website/**`. |
| Docs | `README.md`, `docs/` | User guide, website blocking, development, Windows compatibility. |
| Tests | `crates/*`, `tests/` | `cargo test --workspace --release` runs the Rust unit tests; `npm test` runs the `*.test.cjs` website/companion tests. Playwright scripts drive the real `Still.exe` over WebView2's DevTools port (`tests/rust-launch.cjs`; `test:ui`, `test:todos`, `test:alerts`, `test:websites`, `test:installer`, `test:portability`), plus PowerShell policy tests. See `docs/development.md`. |

## Keep in mind when changing things

- **Safety first.** A strict session is meant to be hard to escape, and a bug can lock users out of their own apps. Never weaken the checks that refuse managed/MDM/domain PCs or PCs with existing app-control policy. Never weaken the IPC sender validation either.
- **Use `npm run demo` (`cargo run -p still-app -- --demo`) or the test scripts** to try the UI. Preview mode never blocks anything. Don't run live protection (`scripts/Test-WindowsProtection.ps1 -RunLiveTest`) unless the user asks.
- **Validate at boundaries.** Input from the screens is checked in `still-core` (`domain`, `alerts`) before the app uses it, and again by the guard. If you add a field, add validation and a test there (and in the Android mirror if it applies).
- **User data must survive updates.** Preferences, alerts, to-dos and history persist across installs, so change storage formats in a backward-compatible way.
- **Paths may be unusual:** Unicode, apostrophes, `%`, `&`, brackets, redirected folders. See `docs/windows-compatibility.md` before touching file URLs, installer paths or PowerShell invocation.
- **Keep dependencies at zero** for the website and the screens (npm devDeps only: playwright). Don't add npm packages or Rust crates casually.
- **Features touch several places.** A user-visible change usually means updating the app, the docs (`README.md`/`docs/user-guide.md`) and the website (`features.html`, `guide.html`, `faq.html`). Refresh the screenshots if the UI changed (see `docs/development.md`).
- Run `cargo test --workspace --release` and `npm test` before finishing. Run the relevant UI script if the UI changed.

## Releasing a new version

1. Bump the version in `Cargo.toml` (workspace), the `.rc` and `.manifest` files of `crates/still-app`, `still-guard` and `still-setup`, and `package.json` + `package-lock.json` (the Android build reads `package.json`).
2. **GitHub release notes:** edit `.github/release-notes.md`. Replace the previous "What's new" section with a short "What's new in vX.Y.Z" section for this release only; keep the install instructions. The release workflow checks that the file has exactly one matching version section, passes it as the release body, and `--generate-notes` appends the commit list.
3. **Website changelog** (https://stillfocus.fyi/changelog, `website/changelog.html`):
   - Add a new `<article class="panel release latest" data-tag="vX.Y.Z">` at the top of `#releases`, with a date, a plain-language bullet list, and download/GitHub links in the same format as the existing entries.
   - Remove `latest`, the "Latest" pill and the primary download button from the previous entry.
4. **Website version everywhere:** update `FALLBACK` in `website/js/site.js` (version, date, size, url, sha256 of the new `Still-Setup-X.Y.Z.exe`). Also update the hardcoded `data-version` / `data-size` / `data-date` fallback text in every `website/*.html`, including the titlebar on every page and `404.html`. You can find them with `grep -rn "1\.0\.1" website` (swap in the old version). JS refreshes these from the GitHub API at runtime, but the static text has to be right for when it can't reach GitHub.
5. Commit, then `git tag vX.Y.Z && git push origin vX.Y.Z` (push the **tag only**; `main` is not pushed yet). `.github/workflows/release.yml` checks that the tag matches `package.json` and `Cargo.toml`, runs the tests, builds `dist/Still-Setup-X.Y.Z.exe` and publishes it as the latest release.
6. **Chrome Web Store (only if `app/browser-extension/` or `app/websites.js` changed):** bump `version` in `app/browser-extension/manifest.json`, run `npm run build:extension`, and upload `release/Still-Extension-<version>.zip` in the Chrome Web Store Developer Dashboard (and Edge Add-ons if published there). This is manual, since `release.yml` doesn't do it and store users only get the new companion this way. The app's unpacked copy (embedded in `Still.exe`) updates itself with the app release. Review can take anywhere from a day to a week, so submit urgent extension fixes early.
7. Wait for that run to finish (`gh run watch`) and confirm `Still-Setup-X.Y.Z.exe` downloads. Then fill in the real date, size and sha256 in `site.js` and push `main`. **Don't push `main` before the release exists.** Pages deploys `website/**` on every push to `main` within a minute or so, but the release takes about 5 to 7 minutes to build. Pushing both together puts the new version's download links live while they still 404.
